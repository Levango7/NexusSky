# Agent 作业硬约束（把踩过的坑变成规则）

> 这份清单来自 2026-10-18 ~ 10-20 一次连续作业里**我自己**踩的坑。每条写清：
> **错在哪 → 造成什么后果 → 硬约束（可执行的句子）→ 机械化在哪（门禁/脚本）**。
>
> 原则：**光写下来没用，能让机器拦住的才算数。** 标「未机械化」的条目，
> 任何人接手都可以把它变成门禁。

## 1. 提交了带 merge 冲突标记的文件

**错在哪**：一次 `git stash pop` 撞了冲突，我没有看 `git status` 就 `git add` + commit，
CHANGELOG 里带进 3 处 `<<<<<<< HEAD` / `=======` / `>>>>>>> Stashed changes`。

**后果**：这种损坏**不会让 CI 变红**。计数门禁按行号读数字，标记行不影响它读数 ——
于是「门禁看起来在工作，其实可能核的是错的行」。仓库历史上还发生过一次：
带 42 处标记的 CHANGELOG 进了 master。

**硬约束**：
1. 提交前**必须**跑 `git status`（看有没有别人的未提交改动）。
2. 提交前**必须**跑 `git grep -nE '^(<<<<<<< |>>>>>>> )'` 全仓验证。
3. 看到别人的未提交改动 → **不要 `git add -A`**，只 add 自己碰过的文件。

**机械化**：`scripts/check-repo-hygiene.py`（CI job `repo-gates`）。
本门禁**已用真事故反证过**：带标记的 CHANGELOG → 拦下；干净文件 → 不误拦。

## 2. 同一份文件里两处数字自相矛盾就提交了

**错在哪**：上面那次冲突提交里，CHANGELOG 正文有 156 个 `[Unreleased]` 小节，
而头部说明与版本索引表还写着 154。我直到下一轮才发现。

**后果**：读者按头部数字理解规模、按正文数实际条目，对不上。
「结构说明」这种**自述性数字**一旦漂移，就与整个项目「声明≠行为」的主线自相矛盾。

**硬约束**：改 CHANGELOG 后，正文小节数、头部说明、版本索引表**三处**必须一致。

**机械化**：同一个 `scripts/check-repo-hygiene.py`（已反证：把头部数字改成 154 → 拦下）。

## 3. 结论建立在没自证过的工具上

**错在哪**：同一轮里我的"量具"错了三次，每次都差点让我去"修"一段好代码：

| 错法 | 现象 | 真相 |
|---|---|---|
| `bash -c "… echo RC=$?"` | 退出码恒为 0 | `$?` 被 PowerShell 插值成 `True`（转义用**反引号**不是反斜杠） |
| 在 WSL 里跑 `coord-status.sh --self-test` | 自测假红 | WSL 里只有 `gh.exe`，`command -v gh` 找不到 → 走了 UNVERIFIED 降级分支 |
| 用正则切 `it(...)` 块数断言 | 报出 289 个"零断言" | 标题里的括号 `[0,360)` 被当成了 `it(` 的结束 |

**后果**：每次都差点把「好代码」判成「坏代码」并去改它。第三次差点给一个**有两条断言**
的用例加重复测试。

**硬约束**：
1. 任何用来**得出结论**的工具（解析器、探针、变异 harness、门禁脚本），
   必须先用一个**已知答案的用例**自证：**正例要能过、反例要能拦**，两个都要。
2. 自证没过 → **不许引用它的输出**。
3. 报告结论时，要说清这个结论是"工具说的"还是"我看的"。
4. **断言型自测还要再走一层变异**：把被测实现改坏，自测必须变红。
   抓不住 = 夹具缺判别性样本 = **这个自测本身是假绿的**，不许拿它当证据。

**机械化**：
- `scripts/check-repo-hygiene.py`、`scripts/check-selftest-coverage.py` 都有
  正例/反例/干净态三个情形的自证（写在各自的模块 docstring 里）。
- **所有门禁脚本一律提供 `--self-test`**；且
  `scripts/check-selftest-coverage.py`（CI job `repo-gates`）会检查
  **凡提供 `--self-test` 的脚本，都必须有 CI job 真的跑它** ——
  没有 CI 覆盖的自测，等于没有自测。
  真实教训：`scripts/coord-status.sh` 的自测就在仓库里，却从没被任何 CI job 跑过，
  它的写回守卫坏了 8 天（把「自动段合法变短」误判成「写坏」，
  `.coord/STATUS.md` 的「在途与占用」段自 2026-10-12 起冻住，
  各 agent 的开工声明发不出去，读板的人只看到 8 天前的过期事实）。
- **自测的假绿也要被抓**：2026-10-21 给 `scripts/e2e-phone-camera.py` 写 `--self-test` 时，
  三个变异体里有一个**没被抓住** —— 夹具里没有任何「像 JPEG 开头但不是 JPEG」的响应，
  于是「魔数只看前两字节」和「看三字节」两种实现表现完全一样。
  补上 `FF D8 00` 这个判别性夹具后才抓住。
  判据：变异体若与原实现**行为等价**，要么补夹具把它区分开，
  要么**显式声明它无害**（并说明为什么无害）—— 不许默默放过。

## 4. 把外部系统的路径写死

**错在哪**：我一度准备把 Android「IP 摄像头」的取图路径写死。

**后果**：安卓侧的内置 IP Camera、IP Webcam、camera-streamer 之类路径各不相同
（`/snapshot`、`/snapshot.jpg`、`/shot.jpg`、`/now.jpg`、`/capture`…），
写死就是猜 —— 猜错了整条链路的验证就作废。

**硬约束**：对接**不由本项目控制**的系统（外部设备、第三方 app、不同厂商的实现）时，
**不写死路径/字段/行为**；要么探测，要么按"响应特征"判定（本次用「返回体是不是真 JPEG」判定）。

**机械化**：`scripts/e2e-phone-camera.py` 的探测逻辑（候选路径 + 按响应体特征判定），
以及 `scripts/e2e-phone-camera.py --phone-ip <ip> --port <port> --discover-only` 可单跑探测。

## 5. 归因也要有证据，不能凭印象

**错在哪**：CI 排队 40 分钟，我第一反应是「仓库没配 `concurrency`」，
于是去加 —— 结果仓库**早就有** `concurrency: cancel-in-progress`（在 `ci.yml` 里），
真正原因是 **runner 容量饱和**（我和另一个会话的 run 撞在一起）。
我加的那段是**重复键**，YAML 里后者覆盖前者，等于白加。

**后果**：多一次无谓改动；而真正的原因（容量）并没有被解决。

**硬约束**：提"缺 X"之前，先 `grep` 现状确认 X 真的缺；提"因为 Y"之前，先找证据。

**机械化**：暂无（软约束）。写在这里就是为了下次先查再改。

## 6. 合并后要验证的东西

**错在哪**：合并冲突解完，我改了头部说明和索引表，却**没核对结构说明的计数**，
导致"声明的数字"与"实际的小节数"不一致（见第 2 条）。

**硬约束**：
1. 合并冲突解完后，除 `git grep` 查标记外，还要核对**该文件自己的自述数字**。
2. 提交前跑一次本仓库的全部门禁（计数门禁 + 卫生门禁 + 相关自测）。

**机械化**：
- `python scripts/check-test-count-docs.py --reports-root <聚合目录> --frontend-json <报告>`（计数）
- `python scripts/check-repo-hygiene.py`（卫生 + CHANGELOG 自洽）
- `python scripts/check-selftest-coverage.py`（自测覆盖）
- `python scripts/check-spi-coverage.py --self-test`（SPI 可验证性）

## 7. 切分支前没提交，`git reset --hard` 把活干抹了

**错在哪**：一个 PR 合进 master 后，我要开下一个 PR。手上还改着三个文件
（`e2e-mjpeg-preview.py` / `ci.yml` / `contributing-guide.md`，都没提交），
我直接 `git checkout master` → 它**被 abort 了**（有未提交改动会挡住），
我看到 "Aborting" 却没停，接着执行了 `git reset --hard origin/master` ——
**那一行把三个文件里两个多小时的改动直接抹掉了**（未跟踪文件不受影响，所以夹具和脚本侥幸没丢）。

**后果**：改动全丢，得重做一遍。更糟的是它**伪装成"已经切好了分支"**：
`git reset --hard` 之后的每一步都成功，输出也正常，不核对就以为没事了。

**硬约束**：
1. 工作区有未提交改动时，**先 commit 或 stash，再切分支**；`git checkout` 报了
   Aborting 就**停下来看**，不要把下一个命令接上去 —— 前一条命令失败时，
   后一条命令的前提已经不成立了。
2. `git reset --hard` 只在**确认工作区干净**（`git status` 空）时执行。
   它是"明确丢弃"的命令，不是"同步"的命令。
3. 批量改完多个文件后，**在切分支/合并之前先提交**（哪怕是 wip 提交），
   让"工作成果"和"分支切换"解耦。

**机械化**：暂无（软约束）。
可考虑做成 `scripts/check-clean-tree-before-reset.sh`，但 git 自身已有
`git reset --hard` 的确认提示，这里更值得做的是**流程**：切分支前先 `git status`。

## 8. 测量本身也会被污染：并发写同一份产物 + 读到半截报告

**错在哪**（2026-10-21 做 PIT 变异测试审计时）：我**同时**跑了两个 PIT ——
一个 standalone（Java 命令行）、一个 Maven 插件版 —— 两者都写
`cloud-backend/target/`。Maven 那次先做 `test-compile`，
把 standalone 那次**正在读**的 test-classes 冲掉了。

**后果**：
1. standalone 那次的报告里 **261 个变异体变成 `RUN_ERROR`**（`numberOfTestsRun=0`，
   也就是"一个测试都没跑到"）。我差点把"变异分数 83% → 49%"读成
   "**我的新测试把分数弄崩了**" —— 其实是我自己污染了数据。
2. 更早一步，我读那个**还在写的** XML 报告，读到"杀掉 583"就下了结论；
   文件写完后真相是"杀掉 320 + error 261"。
   **PIT 是逐个 `<mutation>` 追加写的，半截文件有时能解析成功** ——
   于是你会拿到一个"看起来完整、其实只有一部分"的结果。

**硬约束**：
1. **同一份产物目录上不并发跑两个测量**。A/B 对照必须**依次**跑，
   中间不许有别的构建（`mvn test-compile` 也在写 target/）。
2. **读报告要等它写完**：确认进程已退出，或文件大小/时间戳已稳定。
   拿不准就先看一眼报告里的变异体总数与"生成时"日志对不对得上。
3. `RUN_ERROR` 数量突然变多 ⇒ **先怀疑测量环境**（并发、产物陈旧、被改了一半的源码），
   再怀疑被测代码。变异分数的"退步"有太多种假原因，不查清楚就下结论 = 制造假结论。

**机械化**：暂无（软约束）。
可考虑在 PIT 门禁里把 `RUN_ERROR` 单独计数，并在超过阈值时直接提示
"先查是不是测量环境被污染"（而不是让人去改产品代码）。

## 9. 工具报的"缺口"也要自己复核：区分"真缺口"和"工具的记账问题"

**错在哪**（2026-10-21 变异测试审计）：PIT 报告 `isRateLimited` 有两个存活变异体
（`BooleanTrueReturnValsMutator` / `BooleanFalseReturnValsMutator`）。
按字面看，这是"限流逻辑没被钉住"—— 一个安全缺口。

**但我实测把它改坏了**（手动把 `return true` 改成 `return false`、把 `return false`
改成 `return true`），**新测试全红** ⇒ 那两个 mutator 是「把 true 换成 true /
false 换成 false」，**行为等价**，PIT 记的是"存活"，但它压根没改变行为。

**后果**：如果我不复核就写进结论，就会**报出一个不存在的安全缺口** ——
那比漏报更坏（让人去"修"一段没问题的代码，正是我自己文档里记的那类事故）。

**硬约束**：
1. 工具报出的"缺口"进结论前，**至少挑两条手动复现一遍**（改坏源码 → 看测试红不红）。
   红了才是真缺口；不红就是工具的记账问题，**要显式声明它无害并说明为什么无害**。
2. **区分三类，不要混为一谈**：
   - `SURVIVED` 且手动改坏能复现 ⇒ **真缺口**（行为变了没人发现）；
   - `SURVIVED` 但手动改坏测试仍绿 ⇒ **行为等价**（工具记账问题，声明无害）；
   - `NO_COVERAGE` ⇒ **覆盖缺口**（压根没测到，是另一件事，别当成假绿报）。
3. 报告里给出**三类各自的数字**，不要只给一个"存活 N 个"。

**机械化**：`scripts/check-mutation-baseline.py` 把 `NO_COVERAGE` 与 `SURVIVED`
**分列**（不合并成一个数），避免把"没测到"和"测了但没盯住"混成一句。

## 10. 写"提取型"工具时：属性要按结构定位，不能靠固定窗口或"第一个匹配"

**错在哪**（2026-10-21 端点契约门禁 `scripts/check-frontend-endpoints.py`）：
我写前端→后端的端点比对工具，**提取环节连错四次**，每次都差点让我去"修"没问题的代码：

1. **方法取到了下一个调用的**：我按"匹配位置往后 400 字符"找 `method: 'POST'` ⇒
   把**下一个** `jsonFetch` 的方法算到了当前调用上 ⇒ 报出 **86 处**"方法对不上"的假缺口。
   —— 属性必须**限定在这次调用的实参区间内**（括号配对扫描），不能用固定窗口。
2. **`${...}` 的括号计数错**：见到 `$` 就 `depth=1`，又把 `{` 再 +1 ⇒ depth 永远回不到 0 ⇒
   查询串没被剥掉，路径后面拖着一截 `{p}`。
   —— `${...}` 要当**原子**（配对花括号）处理。
3. **"参数里第一个反引号串"不是 URL**：
   `jsonFetch(url, { headers: { Authorization: \`Bearer ${token}\` } })` 里
   第一个反引号串是 header，不是 URL ⇒ 我把 `Bearer {p}` 当成了端点。
   —— 实参要**按位置**取（第一个实参才是 URL）。
4. **注解里的 `produces = "application/yaml"` 被当成了路径**：我把映射注解里的所有字符串
   都当路径 ⇒ 端点数数成 410，而仓库官方口径是 **409**（差 1）。
   —— 只取 `value=` 或第一个裸字符串；**两个测量口径不一致时，先怀疑自己的提取器**。
5. **自测的夹具没复现它声称的条件**：我断言"已修好的缺口登记要被报出"，
   可夹具里后端**根本没有**那条路径 ⇒ 那不叫"已修好" ⇒ 断言是错的
   （当时我是先红后绿才对上的，说明我写的是"实现的镜像"，不是"需求的检验"）。

**后果**：这版门禁直接合进去，CI 会红 **141 处** ⇒ 团队第一反应是"门禁坏了"，
然后把它关掉 —— **一个误报 141 次的门禁，比没有门禁更坏**。
（本轮最后只报 4 条，其中 **2 条是提取器假象**、2 条是真 bug；
如果不复核就照着改，会去"修"两处根本没错的前端。）

**硬约束**：
1. 提取型工具的每个属性都要**按结构定位**：调用 ⇒ 扫实参区间；注解 ⇒ 取 value/path 实参；
   模板 ⇒ `${...}` 按原子配对。**不许用固定窗口、不许用"第一个匹配"、不许"所有引号串"**。
2. **口径必须与仓库已有的官方计数器对齐**：端点数口径是
   `scripts/count-rest-endpoints.py` / `check-claimed-endpoint-count.py`；
   我另写一套算出 410、官方是 409 ⇒ **差 1 就是我的提取器错了**，不是仓库不一致。
3. **自测夹具必须真的复现被测条件**；写完自测后**故意破坏一次实现**，确认自测会红。
4. **静态检查报出的每一条都要回到源码核对后才改代码** —— 先分清
   "真缺口 vs 工具记账问题"再动手（同第 9 条的纪律，对象从变异体换成静态检查）。
5. 顺带修掉的**量具便携性**问题：`scripts/count-rest-endpoints.py` 与
   `scripts/sync-test-counts.py` 里**硬编码了绝对仓库路径** ⇒ 在别的 worktree / CI 上
   会扫不到文件、**数出 0 个端点**（比没有还误导）。已改为从脚本位置推导仓库根。

**机械化**：`scripts/check-frontend-endpoints.py --self-test` 覆盖上面 ①（区间限定）、
②（`${}` 原子）、③（实参按位置）、④（只取路径实参）、⑤（登记过期会被报出），
共 9 个用例；该脚本的端点数与 `check-claimed-endpoint-count.py` 交叉验证（409 = 409）。
