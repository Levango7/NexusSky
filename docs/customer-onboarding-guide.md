## 一、接入流程概览

NexusSky 客户接入遵循 **评估 → POC → 签约 → 部署 → 培训** 五阶段漏斗模型，总周期约 **2-3 个月**。各阶段层层递进，前一阶段的交付物是后一阶段的输入条件。

### 1.1 总时间线

```
阶段 1          阶段 2          阶段 3          阶段 4          阶段 5
需求评估    →    POC 验证    →    商务签约    →    部署交付    →    培训与运维
1-2 周          2-4 周          1-2 周          2-4 周          1-2 周
(免费)          (5-10 万)       (合同签订)      (项目费支付)    (含在项目费)
```

**最短路径**：8 周（各阶段最短周期，无返工）
**典型路径**：12 周（含评估迭代、POC 调整、部署优化）
**最长路径**：16 周（含多轮需求确认、深度 POC、定制开发、多次培训）

### 1.2 漏斗转化预期

| 阶段 | 进入条件 | 退出条件 | 转化率 |
|---|---|---|---|
| 需求评估 | 客户初步接触 | 需求匹配报告确认 | — |
| POC 验证 | 需求匹配 + 客户同意付费 POC | POC 验证报告通过 | 30%-50% 从评估进入 POC |
| 商务签约 | POC 验证通过 + 客户认可价值 | 合同签订 | 60%-80% 从 POC 进入签约 |
| 部署交付 | 合同签订 + 项目费支付 | 系统上线运行 | 100%（签约即交付） |
| 培训与运维 | 系统部署完成 | 客户独立运维 | 100%（部署即培训） |

### 1.3 角色分工

| 角色 | 需求评估 | POC 验证 | 商务签约 | 部署交付 | 培训与运维 |
|---|---|---|---|---|---|
| **商务经理** | 主导 | 协调 | 主导 | 协调 | — |
| **解决方案架构师** | 主导 | 主导 | 支持 | 主导 | 支持 |
| **开发工程师** | — | 支持 | — | 主导 | 支持 |
| **运维工程师** | — | — | — | 支持 | 主导 |
| **客户技术负责人** | 配合 | 配合 | — | 配合 | 配合 |
| **客户采购/法务** | — | — | 配合 | — | — |

## 二、阶段 1：需求评估（1-2 周）

### 2.1 目标

全面了解客户的技术栈、业务场景与核心诉求，评估 NexusSky 能力匹配度，输出需求评估报告与初步报价方案。

### 2.2 活动清单

| 序号 | 活动 | 负责人 | 周期 | 说明 |
|---|---|---|---|---|
| 1 | **客户技术栈调研** | 解决方案架构师 | 2-3 天 | 发送调研问卷，收集客户飞控型号、通信方式、业务场景、现有系统架构 |
| 2 | **NexusSky 能力匹配评估** | 解决方案架构师 | 2-3 天 | 逐项比对客户需求与 NexusSky 已实现能力，标注匹配/部分匹配/不匹配 |
| 3 | **集成可行性分析** | 解决方案架构师 | 1-2 天 | 评估 MAVLink 协议兼容性、REST/WebSocket 集成路径、部署环境适配 |
| 4 | **模拟器 Demo 演示** | 商务经理 + 架构师 | 0.5 天 | 远程或现场演示 3 机编队 + 应急编排 + Mesh 组网等核心场景 |
| 5 | **初步报价方案** | 商务经理 | 1 天 | 根据匹配评估推荐档位（SDK/私有部署/行业定制）与模块组合 |
| 6 | **需求评估报告评审** | 内部评审 | 0.5 天 | 内部确认评估结论与报价合理性 |

### 2.5 集成可行性分析

| 分析项 | 评估内容 | 结论 |
|---|---|---|
| **MAVLink 协议兼容** | 客户飞控是否支持 MAVLink v2 | PX4/ArduPilot 原生支持；自研飞控需确认 MAVLink 实现 |
| **REST API 集成** | 客户系统是否可通过 REST API 对接 | 155+ 端点，OpenAPI 3.0 规范，标准 HTTP/JSON |
| **WebSocket 实时接入** | 客户是否需要实时遥测推送 | 支持 telemetry/alert/formation/scheduling/decision 五类消息 |
| **部署环境适配** | 客户服务器资源是否满足部署要求 | Docker Compose 单机：4C8G 起步；K8s 集群：按规模配置 |
| **定制开发范围** | 是否需要行业定制开发 | 评估定制工作量，纳入行业定制版报价 |

- 客户明确无需求 → 终止接入流程

- 评估结论为客户需求超出 NexusSky 当前能力范围且无法通过定制满足 → 终止接入流程

## 三、阶段 2：POC 验证（2-4 周）

### 3.1 目标

在客户环境中验证 NexusSky 核心能力，降低正式签约风险。POC 范围聚焦于 1-2 个核心场景，不追求全功能验证。

### 3.2 POC 范围界定

根据客户需求评估结果，选择 1-2 个核心场景作为 POC 验证范围：

| POC 场景 | 对应能力 | 验证内容 | 适用客户 | 周期 |
|---|---|---|---|---|
| **场景 A：单机操控全链路** | Core 模块 | 设备发现 → 任务上传 → ARM → 航点飞行 → RTL → 飞行日志 → 手动控制 | 飞控厂商、轻量集成 | 2 周 |
| **场景 B：多机编队协同** | Core + Fleet (M10) | 3 机编队 → 起飞 → 队形变换 → 协同任务 → 解散 | 整机厂商、方案商 | 3 周 |
| **场景 C：应急指挥闭环** | Core + Emergency (M9) + Mesh (M5) | 灾区测绘 → 覆盖规划 → 组网部署 → 应急服务 → 自愈重构 | 应急救援方案商 | 3 周 |
| **场景 D：安防联动响应** | Core + 4a | 布控球发现 → 报警事件 → 联动规则 → 应急指挥工作流 | 安防/巡检方案商 | 3 周 |
| **场景 E：链路韧性验证** | Core + Mesh (M5) + Relay (M6+M7) | LTE 损伤链路任务流 → Starlink 周期黑洞存活 → 多链路切换 | 通信保障场景 | 4 周 |
| **场景 F：数字孪生验证** | Core + Twin (M13) | 实时镜像 → 轨迹预测 → 场景回放 → 虚实对比 | eVTOL 企业 | 4 周 |

> **选择原则**：优先选择客户最核心的业务场景，且该场景在 NexusSky 已有完整 e2e 验证脚本支持。

### 3.3 POC 环境搭建

POC 环境采用 Docker Compose 部署，确保快速搭建与一致性。

#### 3.3.1 环境要求

| 项目 | 最低要求 | 推荐配置 |
|---|---|---|
| **CPU** | 4 核 | 8 核 |
| **内存** | 8 GB | 16 GB |
| **磁盘** | 20 GB | 50 GB |
| **操作系统** | Linux (Ubuntu 22.04+ / CentOS 8+) | Ubuntu 22.04 LTS |
| **Docker** | 24+ | 26+ |
| **Docker Compose** | v2+ | v2.24+ |
| **Java** | 17+ | 17 (POC 环境构建需要) |
| **网络** | 端口 8080/14540/14550/5173/14600 可用 | 同左 |

#### 3.3.2 部署步骤

```bash
# 1. 克隆项目
git clone https://github.com/Levango7/NexusSky.git
cd NexusSky

# 2. 构建 JAR（POC 环境需要本地构建）
./gradlew build -x test

# 3. 启动 Docker Compose
cd deploy/docker
docker-compose up -d

# 4. 验证服务健康
curl http://localhost:8080/actuator/health
# 期望响应：{"status":"UP"}

# 5. 验证 GCS Web 可访问
# 浏览器打开 http://localhost:5173
```

#### 3.3.3 服务端口确认

| 服务 | 端口 | 说明 | POC 必需 |
|---|---|---|---|
| cloud-backend | 8080 | REST API + WebSocket | ✅ |
| drone-sim | 14540 | MAVLink UDP（模拟器） | ✅ |
| gcs-web | 5173 | 地面站前端 | ✅ |
| link-sim | 14600 | 链路代理（多机场景必需） | 视场景 |

> **注意**：根据经验，部署 Docker Compose 时需确认 docker-compose.yml 中各服务的 `environment` 段配置完整，所有 `${VAR}` 引用均有对应的环境变量注入。重点检查 `S3_BUCKET`、`S3_ENDPOINT`、`S3_ACCESS_KEY`、`S3_SECRET_KEY`、`S3_REGION`、`LIVEKIT_E2EE_ENABLED` 等变量是否正确配置。（来源：2026-09-23-docker-compose-livekit-sfu-config-audit-checklist）

### 3.4 POC 演示与验证

## 九、风险与应对

### 9.1 技术风险

| 风险 | 概率 | 影响 | 应对策略 |
|---|---|---|---|
| **客户飞控 MAVLink 版本不兼容** | 中 | 高 | 阶段 1 评估时确认 MAVLink 版本；v1 需额外适配工作，提前标注 |
| **真机集群验证失败** | 中 | 高 | PoC 阶段如实告知模拟器验证状态；深度 POC 可选真机 SITL 对接；合同中约定真机验证条款 |
| **客户网络环境不支持 UDP** | 低 | 中 | 评估阶段确认网络环境；可配置 TCP 代理转发；K8s 环境可配置 NodePort |
| **客户自研飞控协议非 MAVLink** | 中 | 高 | 阶段 1 评估时确认；非 MAVLink 需额外协议适配开发，纳入行业定制版 |
| **POC 环境性能不达标** | 低 | 中 | 阶段 2 前确认服务器资源满足最低要求；提供推荐配置清单 |
| **卫星接入为占位接口** | 高 | 中 | 如实告知客户卫星接入当前为预留接口（抛出 UnsupportedOperationException）；仿真环境可使用 SimulatedSatLinkProvider |
| **Docker Compose 配置变量缺失** | 中 | 中 | 部署前逐项核对 docker-compose.yml 中所有 `${VAR}` 引用是否在 `environment` 段有对应注入，重点检查 S3、LiveKit 相关变量 |
