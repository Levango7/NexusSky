# DJI 上云 API 2 迁移评估（无真机条件下的测试路径）

> 状态：**评估结论，非执行计划**。本文不改变任何默认配置，也不承诺迁移。
>
> 结论先行：**短期不迁移**。当前仓内的协议级模拟 + 真 broker e2e 已覆盖"无硬件条件下的协议联调"；
> 官方"上云 API 2"的设备模拟器能力更强，但它属于另一条协议栈，迁移是重构而非加装测试工具。

## 1. 要回答的问题

没有 DJI 真机/机巢，能否通过"具备硬件能力的云环境"完成测试与功能实现？

拆成两个子问题：

1. **软件模拟器**能否替代真机做协议联调？——能，且已有两条路径（见 §2、§3）。
2. **云端真机**（远程租用真实设备）是否存在？——检索未发现 DJI 官方或可信第三方提供此类服务；
   无人机测试涉及空域、场地、视距操控、设备绑定码与 License，不具备"云真机"的落地条件。
   此项标记为**不可行（判断）**，不再展开。

## 2. 两条产品线不是同一套协议（事实）

这是本次评估最关键的事实，决定了"官方模拟器能否直接拿来用"。

| 维度 | 本项目当前对接 | DJI 上云 API 2（2026-10-14 发布） |
|---|---|---|
| 协议形态 | MQTT 物模型，逐条 topic 对接 | 新协议栈 + JNI/SDK 本地调用 |
| 下行 topic | `thing/product/{sn}/services` | `thing/property/report`、`thing/service/invoke` 等 |
| 应答关联 | `services_reply` + `tid` | 新栈自有形态 |
| 官方设备模拟器 | 无（本项目自建对端夹具） | 内置，随底座部署 |
| 接入方式 | Eclipse Paho MQTT 客户端 | SDK + 本地调用为主 |

仓内证据：

- `cloud-backend/src/main/java/io/aerofleet/cloud/gateway/DjiCloudApiDeviceGateway.java:66-70`
  定义了 `SERVICES_TOPIC`、`SERVICES_REPLY_FILTER`、`FLIGHT_TASK_METHOD`。
- `docs/protocol-vendor-integration.md:16` 将当前对接标注为 Cloud API 2.0 v2.4.0（MQTT 物模型）。
- 官方旧版文档仍在线（`developer.dji.com/doc/cloud-api-tutorial/`），说明旧协议未被废弃。

**判断**：官方"上云 API 2"的设备模拟器不能作为本项目现有协议的对端；它只能在新协议栈内使用。

## 3. 官方模拟器能做什么（事实，来源：DJI 官方文档）

`developer.dji.com/doc/cloud-api-2-tutorial/cn/simulator.html` 明确列出：

- 虚拟设备创建、启停、批量铺设（单次最多 50 套）；
- 物模型全字段编辑（位置、电量、图传、卫星数等），支持耗电速率调节；
- 故障注入（按部件分类、可设级别/周期/起止时间）；
- 直播推流、航线任务、媒体回传（用媒体库文件冒充拍摄结果）；
- 调试面板：手动下发指令、主动上报事件、推送物模型；
- 场景管理：录制真机行为 → 抽取成场景 → 回放，用于异常场景回归；
- 官方声明可"接入持续集成流水线"。

部署形态：随"上云 API 2"底座部署在服务器上（默认端口 `30812`），**不是纯公有云 SaaS**；
模拟器只扮演设备侧，仍需一个可访问的云端（司空或自建平台）。

## 4. 迁移影响面（代码定位 + 判断）

若决定迁移，改动不是"加一个测试依赖"，而是替换整条 DJI 接入链路：

| 层 | 现有资产 | 迁移后 |
|---|---|---|
| 设备网关 | `DjiCloudApiDeviceGateway.java`（319 行） | 按新协议栈重写 |
| 机巢网关 | `MqttDockGateway.java` | 按新协议栈重写或废弃 |
| 物模型字段表 | `DjThingModelFieldTable.java` | 重新对齐 v2 schema |
| 配置 | `DjiCloudApiProperties`（`aerofleet.dji-cloud.*`） | 新增底座地址/鉴权配置 |
| 单测 | 网关 13 例 + 场景 4 例 + OSD 4 例 + dock 7 例 | 全部失效，需按新协议重写 |
| E2E | `scripts/e2e-dock-mqtt.ps1`（真 broker + 真后端 + 设备侧对端） | 对端与 topic 全部更换 |
| 部署 | 无额外服务 | 新增底座服务与运维 |

**判断**：工作量集中在协议层与测试层，属中等偏大的重构；未做工时估算（缺官方 SDK 试用环境）。

## 5. 收益与代价

**收益**

- 官方故障注入、批量设备、场景录制回放，能力显著强于仓内自建夹具；
- 跟随官方主线，可获得新机型（如机场 4 / M5TD）支持；
- 官方明确支持 CI 接入，长期看有利于回归自动化。

**代价**

- 协议栈重写 + 相关测试全部重写；
- 新增底座部署与运维成本；
- 新产品线发布约 1 个月，成熟度与稳定性**待验证**；
- **仍不能替代真机**：物理层行为（起降、RTK 锁定、图传质量、风场）模拟器不覆盖。

## 6. 建议路径

**短期（当前）**：不迁移。依据：

1. 现有协议级模拟已覆盖命令映射、`tid` 关联、拒绝/超时/断链/并发隔离等软件逻辑；
2. 真 broker e2e（`e2e-dock-mqtt`）已能验证"真后端 + 真 broker + 设备侧对端"的全链路；
3. 缺硬件影响的是物理层与厂商认证，迁移协议栈不解决这一类问题。

**中期触发条件**（满足任一再评估）：

- 业务需要官方新机型或新能力；
- 需要官方级故障注入/批量设备的测试规模；
- 官方模拟器可在自建平台稳定跑通，且 SDK 版本进入稳定期。

**迁移前置条件**：

- 在隔离环境验证官方模拟器能对接自建平台（而非仅司空）；
- 明确 v2 SDK 的许可与商用条款；
- 完成一次试点迁移（单网关 + 单场景），再决定全量。

## 7. 模拟器解决不了的边界（必须写清）

- 真机起降、RTK 固定解、图传画质与延迟、风场扰动；
- 厂商认证、License 与设备绑定流程；
- 场景录制功能本身需要**至少一次真机**作为录制源；
- 现网兼容性：模拟器证明协议层正确，不证明真机固件行为一致。
