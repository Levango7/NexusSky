## 决策：FR-16「多路径备份无缝切换」与 FR-17「度量最优选路」的端到端收口——**暂缓，需协议演进（RREP 接收者地址字段）**

**结论**：FR-16/FR-17 的端到端收口**不以「target 对每个 RREQ 副本回 RREP」的方式上线**。
该方式在组播信道下会引入 RREP 转发循环（StackOverflow）与路由污染，属协议级风险。
正确收口方向是 **RREP 消息加「接收者 sysid」字段**（节点只处理发给自己的 RREP），
属协议演进，需单独立项评估消息结构兼容性。

### 已钉出的边界（证据）

#362/#363 已端到端验证：RREP 沿反向链回源，源节点单次建路只持一条路由；
`RouteTable`/`MultiPathRouter` 的主备 API 在端到端层不经 RREP 积累触发
（`promoteBackup` 永不命中），自愈实际走 FR-15 重建（有 RREQ 往返时延），非 FR-16 无缝切换。

### 侦察发现的真实协议风险（先红后绿过程中实证）

1. `UdpTransportAdapter.send` 发往 `defaultDestination`（组播地址 `meshGroupAddress`），
   `MeshRouter.sendFrame` 的 dest（反向下一跳地址）被忽略——**生产 UDP 下 RREP 也是组播**，
   并非真单播。测试信道 `TopologyChannel.broadcast` 恰好真实模拟了这一组播行为。
2. 若让 target 对每个 RREQ 副本回 RREP（多路径发现的标准 AODV 做法），组播信道下
   中间节点互相转发 RREP 形成回环——5 节点不等价路径拓扑（A—B—D / A—C—E—D）演练
   实测 **StackOverflowError**（C 转发 RREP 经 E，E 又收到并再转发回 C，hopCount 无限递增）。
3. 组播下无关节点也会转发 RREP，源会学到「经无关邻居」的伪路径（路由污染），
   FR-17 的 metric 选路随之失真。

### 为什么必须接收者地址字段

AODV 的 RREP 是单播消息，节点只应处理「发给自己的」RREP。组播信道把单播变广播后，
没有接收者地址就无法判断「是否发给自己」，循环与污染不可避免。
因此干净的 FR-16/17 收口 = `MeshRouteReplyMsg` 加「接收者 sysid」字段 +
节点只处理接收者==自己的 RREP（组播投递但按接收者过滤）。

### 重开条件

1. `MeshRouteReplyMsg` 协议演进立项（加接收者字段），含线上消息结构兼容性评估
   （mavlink-core 编解码 + 版本协商 + 旧节点忽略新字段的向后兼容）；
2. 接收者过滤实现后，用本决策记录的 5 节点拓扑演练复验：多路径发现 +
   主链断无缝切换（FR-16，不发起新 RREQ）+ 度量最优选主（FR-17）三例全绿。

### 本批处置

协议改动已回退（worktree 与 origin/master 逐字节一致），不引入任何组播多路径 RREP 行为。
当前 FR-15 重建路径（#362/#363 已验证）保持为唯一的端到端自愈机制。
